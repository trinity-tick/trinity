# 阶段 3 设计稿：核心代码受控自改（2026-08-28）

> 路线图下一站——本文是设计评估（未实施）。

## 目标

让自进化改写 **trinity/ 核心代码**（检索/判题/编排逻辑）——当前白名单外的领域。

## 核心挑战（与阶段 2 的差异）

| 差异点 | 阶段 2（scripts/） | 阶段 3（trinity/ 核心） |
|---|---|---|
| 影响面 | 单脚本 | 全系统行为 |
| 验证 | py_compile + fulltest | **双环境基准 A/B**（必须） |
| 回滚 | git revert | git revert + **基准回归确认** |
| 风险 | 低（脚本隔离） | 高（检索质量可能回归） |

## 设计：双环境 A/B 门禁

```
1. 补丁生成（同阶段 2，白名单扩展至 trinity/core/client 等**逻辑层**——
   仍排除 adapter/_schema 等数据层）
2. 应用补丁到**工作副本**（git worktree 或临时 checkout）
3. 双环境基准 A/B：
   - 主环境（补丁后）vs fresh 环境（补丁前基线）
   - 跑官方 300q 升级口径（或 holdout 95 问快速版）
   - Session R@10 / QA 必须不降（>= 基线 - 0.01 容差）
4. 全量测试 1261+ 全绿
5. 全过 → 合入主库 + git commit；任一失败 → 弃用补丁（不污染主库）
```

## 前置条件（实施前必须）

1. **基准自动化**：holdout 95 问快速版（~8min）脚本化 + 结果 JSON 化
   （evolve_patch 验证管线可调用）；
2. **fresh 环境隔离**：基准跑 fresh 环境（非主库）——已有机制（seed 777 模式）；
3. **白名单分级配置**：scripts/（auto）/ trinity/ 逻辑层（approval+基准门禁）/
   数据层（禁止）；
4. **成本预算**：每次核心自改基准 A/B ~$0.3-0.5 + 20-40min。

## 门槛与触发

- **准入**：阶段 2 稳定运行 4 周 + auto-evolve 门禁失败率 <20%；
- **触发**：进化引擎指标缺口（如 QA <0.45）→ 目标 → LLM 补丁 → 双环境门禁；
- **人工闸门**：核心自改合入前强制 review（approval 机制）——阶段 3 不做无人值守。

## 风险与回滚

- 基准回归 → 弃用补丁（工作副本丢弃，主库不受影响）；
- 合入后发现回归 → git revert + 基准复跑确认恢复；
- 极端：git reset 到阶段 2 基线（全量回退）。

## 结论

阶段 3 技术上可达（所有组件已有原型），关键是**验证成本与稳定性门槛**——
建议阶段 2 观察 4 周后再启动实施。
